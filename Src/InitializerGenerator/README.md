# IronRuby.InitializerGenerator

IronRuby does **not** discover `[RubyModule]` / `[RubyClass]` / `[RubyMethod]` /
`[RubyConstant]` by reflecting at run time. Each library namespace has a
`LibraryInitializer` subclass that registers its classes, methods and constants, with
every overload's delegate and parameter attributes spelled out. This project is the
Roslyn source generator that writes those classes while `IronRuby.Libraries` and
`IronRuby.Libraries.Yaml` compile.

So a new or changed `[RubyMethod]` needs a build and nothing else. There is no generated
file to regenerate or to commit, and no list of namespaces to keep.

It replaces the reflection half of `Src/ClassInitGenerator` and the checked-in
`Initializers.Generated.cs`, which had to be regenerated by hand: a method added
without doing so was never registered, and a changed `[NotNull]` or
`[DefaultProtocol]` silently kept its old meaning.

## What it generates

- A **library** is a namespace that has `[RubyModule]`-attributed types and is not inside
  another namespace that has them; types in nested namespaces belong to it. Its
  initializer is `<last part of the namespace>LibraryInitializer` (what
  `LibraryInitializer.GetTypeName` expects), so a new `IronRuby.StandardLibrary.Foo`
  gets `FooLibraryInitializer` by existing.
- The output is one file, `Initializers.Generated.cs`, in the compilation. To read it,
  build with `-p:EmitCompilerGeneratedFiles=true`; it is written to
  `obj/<config>/<tfm>/generated/IronRuby.InitializerGenerator/.../Initializers.Generated.cs`.
  `Util/reg-names.py` lists the registrations in such a file, to diff two builds.
- An invalid definition (an instance method with `[RubyMethod]`, a missing `self`
  parameter, two types defining the same class ...) is a build error, `IRGEN001`, at the
  offending member. If the generator itself fails the build fails with `IRGEN999`: an
  exception escaping a generator is otherwise only a warning, and the assembly would
  be built with no initializers at all.

## Order

Modules, methods and constants are written in the order `ClassInitGenerator` used:
the culture-sensitive string order of .NET on ICU (`LegacyCollation.cs`). Ruby can see
it (`Module#instance_methods`, `#constants`), so it is kept, but spelled out in code
so that the output does not depend on the machine's culture or globalization mode.
Overloads of one method are in declaration order, as before.

When this replaced the checked-in files, every library's output was byte-identical to
them; only the order of the libraries within the file changed (now by namespace),
which nothing reads.

## What must stay in step with the runtime

The generator runs inside the compiler and cannot call into `IronRuby.dll`, so it
restates three small pieces of it against compiler symbols:

| Here | Runtime |
|---|---|
| `LibraryDef.EncodeCustomAttributes` | `LibraryOverload.EncodeCustomAttributes` |
| `KnownSymbols.AppendQualifiedName` | `RubyContext.GetQualifiedNameNoLock` |
| the restrictions default in `LibraryDef.ReflectTypes` | `RubyModuleAttribute.GetRestrictions` |

Enum values (`RubyMethodAttributes`, `ModuleRestrictions`) and the number of overloads
`DefineLibraryMethod` takes inline are read from the referenced assembly, not copied.
`LibraryInitializerOverloadAttributes1` in IronRuby.Tests compares the parameter
attributes of every registered overload with what the runtime reads from the method.

## Limits

- It looks at the whole compilation on every change (`CompilationProvider`), which is
  fine for a command-line build and makes an IDE redo the work as you type.
- It targets `netstandard2.0` and Roslyn 4.8, the requirements for loading into any
  current compiler, whatever IronRuby itself targets.
